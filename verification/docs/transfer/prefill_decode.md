# Prefill-to-decode transfer: model and results

Canonical code-to-model reference for the prefill-to-decode KV-cache transfer
subsystem under `TpuSyncVerify/Transfer/`. All `file:line` citations in the
Lean modules and in this document are to tpu-sync **`50b0774`**.

This file is the short map: routing from C++ to the owning Lean module, what is
proved, the model boundaries, the assumptions and the mutants. Each `trace_*`
theorem's docstring names the C++/Python test it replays (52 upstream tests:
46 C++, 6 end-to-end) with `file:line`; there is no separate test table.

## Shipping C++ vs. modelled design alternatives

Two modules parameterize both the **shipping C++ behavior at `50b0774`** and a
**non-shipping design alternative** so both can be compared formally:

| Module | Parameter | Shipping C++ behavior (`50b0774`) | Modelled design alternative (not in shipping C++) |
|---|---|---|---|
| `PrefillDecode/PeerIsolation.lean` | `SlotPolicy` | **`SlotPolicy.unboundedPerPeer`**: `StartRead` (`mgr.cc:863-871`) acquires staging from `StagingBlockAllocator` with no per-peer cap. `numSlots` wedged reads to `Peer.sick` exhaust `freeSlots = 0` and cause healthy reads to fail slot admission (`trace_sick_peer_starves_staging_slots`, matching `DISABLED_SickPeerStarvesStagingSlotsForHealthyPeer` at `kv_cache_manager_with_transfer_control_test.cc:1041-1089`). | **`SlotPolicy.perPeerQuota maxPerPeer`**: Caps staging slots held by any single `remote_endpoint` at `maxPerPeer < numSlots`. Proves `Peer.sick` holds at most `maxPerPeer` slots (`reachable_sick_staging_le_quota`) and healthy peers are always admitted (`reachable_quota_admits_healthy`). |
| `PrefillDecode/ReceivePoll.lean` | `stepM (poll : Bool)` | **`stepM true` (`poll = true`)**: `CompleteReadWithDetails` (`mgr.cc:966-970`) checks `IsReadyToComplete()` (`recv.cc:430-436`) and calls `Finish()`. Safe (`Recv.reachable_safe`), but if the poll fires in the window after all H2D futures are ready and before the last callback runs, the last callback sees `draining_` and skips `RecordTransferDuration`/`RecordH2dComplete`/`RecordEnd` (`trace_poll_skips_metrics`). | **`stepM false` (`poll = false`)**: Removes the poll-side `IsReadyToComplete` finish so only the last H2D callback finishes a `num_layers() > 0` session (requiring a zero-layer receive to finish at creation like `TransferSendSession::StartPush` at `send.cc:302-305`). Preserves all safety and settlement properties (`noPoll_safe`, `noPoll_can_settle`) and guarantees metrics on success (`noPoll_metrics_on_success`). |

*(Note: in `PeerIsolation.lean`, `Backend.tcpBlocking` and `Backend.grpcAsync` are both shipping C++ control-plane backends.)*

## System & model boundaries (horizontal, upper, and lower)

The prefill-to-decode Lean model sits between three explicit boundaries:

| Boundary | In scope / Modelled in Lean | Out of scope / Abstracted at boundary |
|---|---|---|
| **1. Horizontal boundary (Prefill-to-Decode / Symmetric vs. Other Subsystems)** | **Prefill-to-decode ("symmetric") KV-cache transfer**: layer-wise producer registration (`NotifyForRead` / `register_read`), consumer pull & load (`StartRead` / `start_read`), D2H → H2H → H2D pipeline (`TransferSendSession`, `TransferReceiveSession`), and outcome polling (`CompleteReadWithDetails` / `poll_stats()`). | **Pool resharding ("asymmetric TP")** (`PoolReshardPush`, `PoolReshardRegisterRecv`, `ReshardSendSession` / `ReshardReceiveSession` in `reshard_{send,receive}_session.{h,cc}`, `active_pool_reshard_{sends,recvs}_` polled in the same `CompleteReadWithDetails` loop at `mgr.cc:940-957, 995-1021`, `pool_reshard*`), **`RaidenController`** (`raiden_controller.*`, `Controller/ReadRemote.lean`), and **`kv_cache_store` / `host_offload_backend`**. |
| **2. Upper boundary (External Serving Engine: vLLM / SGLang ↔ `tpu-sync` API)** | **`tpu-sync` API & Engine Caller Contract (`Pipeline` A4, `MultiRequest.lean`)**: `NotifyForRead`, `StartRead`, and `CompleteReadWithDetails` (`done_sending`, `done_recving`, `failed_recving`). `MultiRequest.lean` models when the caller may recycle prefill HBM (`.recyclePrefill`: only after `send.published ≠ none`, backed by `PrefillHbmSafe`) or read/recycle decode HBM (`.nextRequest`: only after `recv.published ≠ none`, backed by `DecodeHbmSafe`), and detects premature HBM recycling via `wroteReleased`. Note that `tpu-sync` at `50b0774` has **no caller-invoked cancel-read API on the prefill-to-decode path** (the only cancel-like public entry point, `cancel_request_blocks_if_unclaimed` in `tpu_sync/api/torch/reshard_client.py`, is reshard-only and outside boundary 1); sessions cancel only on `tpu-sync`'s internal session deadline (each session's `deadline()`, compared in `CompleteReadWithDetails` at `mgr.cc:919` for sends and `mgr.cc:971` for receives) or transport error (`4efb0dd`). | **External vLLM / SGLang Python orchestration** (outside this repository; e.g. the vLLM `TPUConnector` from `tpu_inference.distributed.tpu_raiden_connector` that `examples/single_host_disagg/prefill.sh:46` / `decode.sh:44` configure): bootstrap/proxy servers, scheduler queues, external KV block allocators, and engine-side (Python) timeouts. If an external engine times out a transfer in Python and frees HBM *before* `tpu-sync`'s `poll_stats()` publishes settlement, it violates `Pipeline` A4 (`wroteReleased` in `MultiRequest.lean`: in-flight D2H/H2D DMA can read or overwrite recycled HBM). |
| **3. Lower boundary (Session–Transport Callback Protocol vs. Raw Socket / Wire I/O in `BlockTransport`)** | **Session–transport callbacks, block plans & control-plane worker pool**: (a) incoming push lease (`begin_incoming_push` / `end_incoming_push`, `pushBegin` / `pushEnd`) pinning host staging (`in_flight_ > 0`) across session expiry (`Receive.lean`, `Pipeline.lean`); (b) callback ordering `OnLayerReceived` (`h2dBegin l`) before `OnBlocksReceived` (`netAccount`, `Receive` A4); (c) within-layer block-index gather, dual-permutation `BuildLoadCopyPlan` sorting (`remote_order` / `local_order`), and contiguous-run DMA coalescing (`BuildCoalescedCopySpec`) in `BlockOrdering.lean`; and (d) control-plane handshake worker-pool occupancy (`TcpControlPlaneBackend::SendPullRequestBlocking` vs. `GrpcControlPlaneBackend::SendPullRequest`) in `PeerIsolation.lean`. | **Raw socket I/O, wire framing & internal `BlockTransport::layer_progress_`**: Per-layer block accumulation inside `BlockTransport::HandleIncomingPush` (`layer_progress_` keyed by `{uuid, layer}`, `bt.cc:498, 511`; `on_layer_received_called`, `bt.cc:559-561`) sits below **`Receive` A1** (fires `OnLayerReceived(l)` at most once when layer `l` completes). Raw TCP socket loops (`ReadExact`/`WriteExact`), per-read socket timeouts (`ReadExactWithTimeout` / `ReadVExactWithTimeout` via `poll()` in `tpu_sync/transport/lib/socket/util.cc:322-424`, configured in `bt.cc:76-101`, `e7c933f`), wire headers, byte-length checks, TCP connection pooling, and raw pointer `memcpy` in `tpu_sync/transport/block_transport.cc` are collapsed into atomic step transitions (`land l`, `h2hDone l ok`, `cancel` + `pushEnd`). Inspect `block_transport.cc` directly for raw socket/wire behavior and cite `Receive` A1 & A4 as the model boundary. |

## Boundary assumptions (`A1`..`An`): discharged vs. external contracts

Every module documents its numbered assumptions (`Receive` A1–A4, `Send` A1–A6,
`Pipeline` A1–A4). When answering questions, distinguish assumptions that are
**discharged by another Lean module**, **enforced directly by C++ control flow**,
or **external caller/transport contracts**:

| Assumption | What it states & C++ location (`50b0774`) | Status |
|---|---|---|
| **Pipeline A4 (Engine caller contract)** | Decode reads destination HBM only after `poll_stats()` reports `done_recving`; prefill frees/reuses source HBM for a registered transfer only after `poll_stats()` reports that transfer settled (`done_sending` or `failed_recving`, `mgr.cc:926-936, 981-990`). | **Receive A4 / Pipeline A3 (Transport ordering & single sender per layer)** | For the request that completes a layer, `HandleIncomingPush` (dispatched from `HandleCustomRequest`, `bt.cc:303`) calls `OnLayerReceived` (`bt.cc:601-608`) before `OnBlocksReceived` (`bt.cc:614-615`) on the same thread, and `ExecuteLayerH2d` pushes the future into `h2d_futures_` before returning (`recv.cc:633-636`). | **Send A1 (At-most-once `StartPush`)** | `StartPush` runs at most once per send session, after `NotifyForRead` registration and `ValidateAndBeginPull` (`pull_started_` atomic claim, `send.cc:116-130`). | **Discharged in Lean** (`Send.PullClaimed`, `Pipeline.HandshakeSafe`, `BlockOrdering.validateRequestedBlocks_iff`) |

| **Send A5 (No consumer `Ack`)** | The client-side `SendAck` (`grpc_control_plane_backend.cc:365`, `tcp_control_plane_backend.cc:662`) has no non-test caller at `50b0774`; the server-side handler `OnAck → HandleAck → AckSend → Finish()` (`mgr.cc:1374-1376, 1551-1554, 1617-1628`) is wired but never triggered in-repo, so it is excluded. | **Dead path at `50b0774`** |

| **Pipeline A2 (Delivery ordered after push callback)** | `Pipeline.lean` models `h2hDone l true` before `land l`; in C++ the receiver lands the layer payload (`ForEachPayload` loop, `bt.cc:415-469`) before sending the ack that triggers the sender's callback (`bt.cc:617-620`).
