# Upstream `00e946e3` sync: manager-owned session bookkeeping, host-memory transfers, and what changed in the models

Canonical sync facts: `../../upstream-rechecks.md` row 2026-11-09 and `findings/README.md` §History (2026-11-09). This entry records only the delta in model understanding.

[OBS 2026-11-09] **A failed pull reply no longer flips a settled receive.** `TransferReceiveSession::Start`'s `on_response` lambda now finishes only `if (!pull_status.ok() && !self->draining_)` (`32568d35`, with the comment that a receive settled before a slow control reply "keeps its verdict" — a host destination with no H2D step makes the data outrunning the reply likely). That is the `Receive/Coverage.lean` open question ("can a reply fail after its data landed?") answered by the C++, and F14's only production-reachable prefill-to-decode case (3) closed. `Recv.pullReply false` gained the `draining` guard (`if ok ∨ draining then life else life.finishLocked false`); the old order is mutant G13 and *survives* — safety never depended on which verdict wins, only the publication did. Receive branches 37 → 35, uncovered 13 → 11; the ripple into `Pipeline/Progress.lean` was one witness state (`s.recv.life.endOpLocked` instead of `(finishLocked false).endOpLocked`). `FinishLocked` itself still records the error before `if (draining_) return;` on both receivers, so F14's `EndIncomingPush`, `UnregisterActivePlan`, destructor and deadline-sweep-race cases stand.

[OBS 2026-11-09] **Host-memory transfers are a different data path, not a different protocol — kept as a boundary.** `BlockLocation::kHost` on the producer (`TransferSendSession::StartPush`: no staging, `d2h_layer_futures_` pre-resolved OK, straight to `SendNextLayer(0)`) is the device model after the prefix `beginPull, start, (d2hBegin, d2hIssue true, d2hReady, d2hEnd)^n` (`Send.trace_host_source_prefix`); the only over-approximation is `wake false`, which a host send never produces. On the consumer (`TransferReceiveSession::SettleHostLayer`) a layer report increments `num_completed_layers_` with no op and no future, and the last one settles the receive *inside the push lease* via `RecordNetworkCompleteLocked(true)` → `FinishLocked()` — the arm the notes called dead is dead only on the device path. A `Cfg` flag was rejected on both sides: on the receive it would violate `CountersOrdered` (`issued = ready = retired = 0` while `completed` climbs), on the send it would add a `start` branch that `Pipeline` / `MultiRequest` build on, for an exact simulation argument. `CheckHostMemoryTransferSupported` (`num_host_layers() == num_layers()`, `!staging_allocator_->LeasesHostBlocks()`) keeps host transfers away from `LayerStaging` and `PeerIsolation`, and a kHost `StartRead` leases no staging slot at all (outside F5's pool). Candidate follow-up model: a `Recv` with the H2D events replaced by one `hostLayerSettle`.

[OBS 2026-11-09] **The sub-plan chain is now one req_id-keyed table shared by both roles, and it reports directly when it has no entry.** `25f7d8a7` merged `recv_chains_` / `send_chains_` into `sub_plan_chains_` with `SubPlanChainProgress{sub_sessions, completed, failed, last_activity, anchored}`; `NoteSubPlanRegisteredLocked(req_id, session, index, count)` *erases* the entry on `count <= 1` (the old code ignored single plans) and re-anchors fresh on index 0; `RecordPoolReshardTerminalLocked(is_recv, req_id, uuid, session, status)` finds the sub-plan by `std::find` on the session pointer and, with no entry (or an unanchored entry that does not hold the session), inserts the request's terminal directly. The `SubPlanChain` worker model was rewritten on `ChainProgress{present, subSessions, completed, failed, anchored}`; [SUPERSEDED → post-audit `OBS` below: A5 does **not** hold unconditionally in C++ because `CompleteReadWithDetails` skips `IsDraining()` sessions while `SweepSubPlanChainsLocked` erases `failed || completed` without checking `!sub_session->Done()`, and A6/A7 were triaged against `ReshardCoordinator` / `BuildPoolReshardPlan`] `reachable_worker_safe` now needs three assumptions the old code did not: A5 the deadline arm runs before the sweep in the same `CompleteReadWithDetails` (so a stalled chain's open sessions are failed before the entry is erased), A6 no single-plan registration arrives while a sub-plan of the req_id is seated, A7 one session per slot. Each has a mutant (`mutant_no_deadline_arm_reports_done_after_sweep`, `mutant_single_plan_registration_erases_live_chain`, `mutant_slot_overwrite_reports_stray_done`). Whether A6/A7 are facts about the callers or latent defects is not yet established — parked as candidate hazards in `../../loose-ends/parked.md`.

[OBS 2026-11-09] **Push-session retirement no longer clears the table.** `CompleteIncomingPush` sets `done_` without `layer_progress_.clear()`; `GetOrCreatePushSession` hands out the map's session only while `!IsDone() || HasAdmittedPosts()` and otherwise seats a fresh one, and `HandleIncomingPush` ends with `DeletePushSession(session)`. `Transport.retire` (`entry := none`) now reads as "the fresh session a later stream gets"; [SUPERSEDED → post-audit `OBS` below: on the sender-declared contract with multiple streams, a stream holding the pre-retirement `shared_ptr<BlockTransportServerPushSession>` hits `streams.landed > streams.declared` and fails `TransferReceiveSession` via `EndIncomingPush`, and `Transport` also needs explicit fresh-UUID assumption A5 because `ForgetPushProgress` runs unlocked] a concurrent stream that already holds the retired session finds the latched entry and cannot re-dispatch, so the model admits one dispatch the C++ refuses — an over-approximation on the dishonest side only (A4). The chunk-count contract is still `completed_chunks == expected_chunks` with no over-count rejection (R-B unchanged).

[OBS 2026-11-09] **Post-sync audit corrections (`SubPlanChain` A5–A8, UUID-retirement assumptions, `Reshard/Pipeline` coverage, and Peregrine hazards).** Two adversarial audit passes on the `00e946e3` re-pin caught five soundness/faithfulness issues in our initial sync prose and models:
1. **`SubPlanChain` A5 fails in C++ on `IsDraining() && !Done()` siblings and on intra-poll `EndOp` across `session->mu_` scopes (both folded into F13):** `KVCacheManagerWithTransfer::CompleteReadWithDetails` gates its deadline arm on `if (!session->IsDraining())` (and idle `!IsDraining()` sessions settle `done_ = true` synchronously inside `RetireSettledSessionLocked` before `SweepSubPlanChainsLocked`), whereas `SweepSubPlanChainsLocked` erases `progress.failed || progress.completed` tombstones without checking `!sub_session->Done()`. On a single non-retried multi-window chain whose first sub-plan failed, a sibling already in `IsDraining() && !Done()` with `OkStatus()` (`ReshardSendSession::EndOp` during unlocked `ReleaseDataConnectionsAfterSend`, or `ReshardReceiveSession::FinishPoolH2d` before `EndOp`) is skipped by the deadline arm, survives the tombstone erase, and settles into `it == sub_plan_chains_.end()` on the next poll — emitting `done_sending_` / `done_recving_` after `failed_recving_` (A5b). In addition, `CompleteReadWithDetails` acquires `session->mu_` separately in `RetireSettledSessionLocked` (`Done()`) and `SweepSubPlanChainsLocked` (`!Done()`): if an unanchored `index >= 1` sub-plan's `EndOp()` sets `done_ = true` (`OkStatus()`) in between, `SweepSubPlanChainsLocked` marks the live chain stalled (`failed_recving_`, `progress.failed = true`) and clears `progress.sub_sessions` while `progress.anchored` stays `false`, so the next poll hits `sub_it == progress.sub_sessions.end()` ahead of `if (progress.failed || progress.completed)` in `RecordPoolReshardTerminalLocked` and emits `done_*` after `failed_recving_` (A5c). `SubPlanChain` now splits `draining` and `inFlight` from `done` on `SubSession`, models mid-poll `EndOp` settlement, witnesses both C++ bugs, and proves `reachable_sweepWaitsForOpen_safe` without A5b or A5c (holding tombstones while `sessions_` still has any unretired entry for `req_id` and checking `failed || completed` before `!anchored` in `RecordPoolReshardTerminalLocked`).
2. **A6–A8 and dual-role triage:** Within one sub-plan (`plan.uuid`), dual-role seating is impossible (`BuildStartTransferForTarget` sets both `is_sender = true` and `is_receiver = true`, so `KVCacheListener::HandleControlRequest` routes Phase 1 arm to `PoolReshardPush` instead of `PoolReshardRegisterRecv` and never arms a receive session on that unit). Across calls, however, C++ enforces neither A6 nor A7: pipelined `ReshardCoordinator::Coordinate` stages sharing one producer registration `req_id` (`PipelinedDestinationStagesShareOneRequestClaim`) or a retry shrinking to `count = 1` erase or re-anchor `sub_plan_chains_[req_id]` mid-flight (breaking A6), and a sparse-window sender absent from window 0 (`anchored = false`) never re-anchors on a same-`req_id` retry, overwriting `sub_sessions[index]` so Attempt 1's session hits the `!anchored` stray arm to emit premature `done_sending_` (breaking A7); `CoordChainState`'s `OneWindowStagedPerDestination` also rests on explicit assumption A8 (single-window exclusive `PoolStagingStorage` capacity).
3. **Single-UUID-generation assumptions (`Transport` A5, `PoolStaging/Registration`) & `Reshard/Pipeline` pairing:** `BlockTransport::ForgetPushProgress` and `KVCacheManagerBase::ReleasePoolStagingLeases` run outside `KVCacheManagerWithTransfer::mu_` after `std::erase_if` ran inside the same `mu_` hold (F16), so `PoolStaging/Registration` dropped its dead `hasInFlightUuid` guard on `.settleSession` and both modules now state single-UUID-generation across poll retirement explicitly; `Transport.lean` also distinguishes fresh-lookup `retire` from pre-retirement `shared_ptr<BlockTransportServerPushSession>` retention on sender-declared pushes (`streams.landed > streams.declared` → `EndIncomingPush` failure); and `Reshard/Pipeline/Coverage` now pairs `ReshardSendSessionTest.PoolOrderInvertedFromStorageOrderPassesTransportValidateChunks` (`12 / 60` one-pool branches covered, closing the `landStream` transport gap).
4. **Dormant Peregrine (`e082548c`) receive-lease bugs parked:** `BlockTransportServerPushSession::ResolveRecvBuffer` / `RejectPost` / `OnPeregrinePostComplete` have three `PostLease` bugs (`PostKeyOf` `{remote_id, local_id, shard_mask}` collision across co-hosted/same-`node_id()` senders or concurrent `AsyncPush`es, `RejectPost` lock-gap `PostLease` leak deadlocking `~KVCacheManagerWithTransfer`, and post-write `BeginIncomingPush` on sender-addressed RDMA writes), parked in `../../loose-ends/parked.md` while `PeregrineTransportAdapter::Create` leaves `recv_post_callback = nullptr`.
