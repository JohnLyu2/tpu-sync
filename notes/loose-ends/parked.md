## Propagate the real push-failure status through `EndIncomingPush`
**Status:** parked 2026-10-06
**Context:** Since upstream `4efb0dd`, `BlockTransport::HandleIncomingPush`'s `absl::Cleanup` reports every early return to the receive session as `InternalError("Incoming push failed")` (`tpu_sync/transport/block_transport.cc:376-381` at `50b0774`), and `end_incoming_push` finishes the session with that status (`tpu_sync/core/kv_cache_manager_with_transfer.cc:239-242`). The actual cause — handshake/payload read timeout (`e7c933f`), size mismatch, `OnLayerReceived`/`OnBlocksReceived` error — is only in the transport log, so `failed_recving` (and the connector's retry policy) cannot tell a dead peer from a corrupt stream. Observability, not correctness: the Lean model does not distinguish error statuses.
**Why parked:** no behavioural impact; the re-pin and the per-peer-admission proposal came first.
**To resume:** capture the status of the failing step in a local `absl::Status push_status` inside `HandleIncomingPush` (set before each `ABSL_RETURN_IF_ERROR`, or wrap the body in a lambda and pass its result to the cleanup), pass it to `EndIncomingPush(uuid, status)`; add a case to `RecvLifecycleTest.FailedIncomingPushImmediatelyFailsSessionAndReleasesStagingBeforeDeadline` asserting the session status code equals the injected read error (`DeadlineExceeded`). Small CL; could ride along with any change touching that hook.
**Effort estimate:** ~30 min
**References:** ../journal/2026-10/2026-10-06-upstream-50b0774-merge-and-citation-repin.md

**Status:** parked 2026-10-07

## Missing C++ test: a send blocked in `AcquireWithTimeout` woken by a freed slot (and its `deadline_` expiry path)
**Status:** parked 2026-10-09
**Context:** Verified against `50b0774`. `TransferSendSession::AcquireStagingWithRetry` (`tpu_sync/core/transfer_send_session.cc:234-268`) polls `StagingBlockAllocator::AcquireWithTimeout` (`tpu_sync/core/kv_cache_manager_with_transfer.cc:1226-1257`) in 1 ms slices, re-checking `draining_ || done_` between slices and returning `DeadlineExceeded` at `send.cc:264-266` once `deadline_` passes. Three exits exist: slot freed, own `Finish`, deadline. Only the `Finish` exit has a test (`CancelledWhileWaitingForStagingExitsWithoutShuttingDownAllocator`, `transfer_send_session_test.cc:221-264`). No test blocks a *live* send on a full pool and frees a slot to wake it, and none drives the wait to `deadline_` expiry. The Lean `Send` model deliberately abstracts this wait away: `.start` is instant acquisition, `.cancel` instant refusal; there is no "waiting for a slot" state, so no liveness theorem for the wait exists (see `verification/docs/transfer/prefill_decode.md` §Boundary assumptions, and the case-6 agent run in `../sessions.md` 2026-10-09). Surfaced by the agent-test negative control, which correctly answered "no theorem" and then found this gap.
**Why parked:** the gap is in upstream tests, not in the model; extending `Send.lean` with a wait state buys little (the 1 ms poll loop makes the liveness argument trivial once `Finish` and slot release are both visible) and the per-peer admission follow-up (entry above, variant (a)) would subsume it if the owners choose wait-at-cap.
**To resume:** (1) add to `transfer_send_session_test.cc` a sibling of the `CancelledWhileWaiting…` test: pool of one slot held by a dummy session, start the push, assert the session is still live after >1 ms, release the slot, assert the push proceeds and settles; (2) a second case with `deadline_` in the past that asserts `DeadlineExceeded` and no staging held; (3) run via `notes/empirical/oss-bazel-test-recipe.md`; (4) offer upstream as a small test-only PR; (5) only if wait-at-cap is adopted, model the wait as a blocked `start` in `Send.lean`.
**Effort estimate:** ~1 h for the two tests; ~half-day if the Lean wait state is added.
**References:** ../durable/prefill-decode-transfer-settle-and-layer-readiness-invariants.md, verification/docs/transfer/prefill_decode.md §Boundary assumptions and the test names in the `Send.lean` trace docstrings, `../sessions.md` 2026-10-09
